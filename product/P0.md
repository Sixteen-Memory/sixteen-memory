# v0.2.0 intelligent memory preview

Historical development notes. This preview did not replace the recorded v0.1.0 production baseline.

## Implemented paths

- `POST /v1/ingestions`: conversation → extraction → exact-source validation → maintenance decisions → automatic commit or pending review.
- `GET /v1/ingestions?user_id=...` and `GET /v1/ingestions/:id`: inspect processing state.
- `POST /v1/ingestions/:id/resolve`: `{"approve":true|false}` approves the whole batch or clears the candidates.
- `GET /v1/memories/:id/evidence`: primary evidence and supplementary evidence associated with specific versions.
- `POST /v1/search`: `mode=lexical|semantic|hybrid`, with lexical still the default; non-lexical modes require one user scope.
- `POST /v1/reindex`: up to eight records per batch, returning `next_cursor`; reindex after changing the embedding provider, model, or revision.
- Corresponding SDK and console entry points, while preserving explicit APIs.

## Implementation is not a quality result

Initial engineering validation used fixture providers. A later, explicitly authorized small local text-model pilot was recorded in the original workspace's private November 4, 2026 test notes; that authorization did not cover production use. Semantic paths have not been validated with real embeddings. There are no matched Mem0 performance results, and intelligent features were not released to production.

### Writes and safety

Each request allows up to 32 messages, 16,000 characters, and eight facts. Conversation roles are limited to user/assistant. Evidence must be an exact quote from a user message; assistant text is context only. Confirmed business events use explicit writes with `source.type=business`; conversation text cannot promote itself to that authority.

Finding an exact quote proves that the quote exists, not that the model's paraphrase is faithful. A second maintenance call checks support but can still fail. The 0.95 threshold is an operating rule, not a calibrated probability. Review is the default; automatic mode is only appropriate for low-risk information. Privacy-sensitive information, business status, and high-risk use cases still need human review.

Exact duplicates retain one current memory and add evidence. A newer fact for the same slot may update an older automatically created record. Prior content remains in history, and prior evidence stays attached to its version. Ambiguous time, manual records, non-exact duplicates, questionable scope, or insufficient support require review. Approved records become explicit; future automatic replacement requires review again.

Concurrency checks use a user-scope revision and target versions. If the source scope changes while a model is running, reject the entire batch. Models cannot target out-of-scope IDs. `request_id` is deduplicated per credential for 30 days; retrying a failed or in-progress request does not call the model again. A distinct request ID represents a new call.

Deletion clears current content, history, FTS, vectors, and supplementary evidence, and clears raw content from pending tasks in the same user scope. Completed tasks retain minimal result IDs; deleted records cannot be restored by replaying old tasks. Review candidates expire after 24 hours. Backup-copy boundaries remain separate, as described in deployment notes.

### Semantic retrieval scope

Vectors live in the same SQLite store. Retrieval uses normalized cosine similarity and RRF fusion with FTS. Semantic embeddings use Qwen; the operator configures the actual model, workspace, and region. This is a small, inspectable implementation, not a large ANN cluster: up to 1,000 active memories per user and 2,048 dimensions. Each vector is tied to a memory version and a fingerprint of endpoint/provider, model, API mode, dimensions, and explicit revision.

There is no silent semantic fallback. Missing configuration or incomplete coverage returns an error unless the caller explicitly requests `fallback:"lexical"`, which returns degradation/warning information. With embeddings enabled, explicit writes prepare vectors before committing; embedding failures do not save the new record. Existing records require explicit batched reindexing. No automatic paid full-database reindex occurs.

### Calls and budget

Extraction, embeddings, and answer generation are configured separately. Endpoints come only from server configuration, not caller input. Calls require HTTPS, do not follow redirects, enforce size/time limits, and do not automatically retry external requests.

A deployment reserves at most 200 intelligent calls per UTC day, including failed requests. An extraction job reserves two or four calls. This is a request-count gate, not a monetary billing cap, and it cannot stop a provider from continuing work after a local timeout. Define customer budgets before expanding capacity.

Configuration is disabled by default. Put secrets only in `.dev.vars` or Worker secrets, never ordinary variables:

```text
EXTRACTION_ENABLED=true
EXTRACTION_BASE_URL=https://<approved-provider>/v1
EXTRACTION_MODEL=<approved-model>
EXTRACTION_API_KEY=<secret>
EMBEDDINGS_ENABLED=true
EMBEDDING_PROVIDER=qwen
EMBEDDING_API_STYLE=openai-compatible
EMBEDDING_BASE_URL=https://<approved-provider>/v1
EMBEDDING_MODEL=<approved-embedding-model>
EMBEDDING_API_KEY=<secret>
EMBEDDING_DIMENSIONS=1024
EMBEDDING_REVISION=1
```

The compatible path requires Chat Completions JSON output and embedding support. Actual compatibility needs approved-credential verification; not every model is compatible. Do not transfer employer gateway credentials into this product. See [provider policy](PROVIDER_POLICY.md) for the Qwen native mode and compatibility controls.

## Comparative evaluation

`node eval/run.mjs` performs preflight only by default. Execution needs the separate `eval/` dependencies, environment configuration, `EVAL_APPROVED=yes`, and `EVAL_MAX_CALLS`. See [evaluation guidance](eval/README.md).

The five conditions are no memory, recent history, raw lexical memory, SixteenMemory intelligence, and Mem0 OSS. Answer model, context-character budget, output cap, and order are fixed. Retain per-case answers, context, request summaries, actual usage, and latency. Missing or failed calls are not zero scores. There are no automatic retries or monetary cost claims without verified pricing.

The six built-in cases are synthetic development diagnostics, not a blind benchmark or public result. Public evaluation material can be adapted to the input protocol, but no private employer/customer data was imported and no paid official leaderboard evaluation was run as part of that work.

The comparison framework passed fixed-response smoke checks across all five paths: 5/5 paths, 16 simulated provider calls, zero real-model calls. The isolated Mem0 adapter was exercised for add, search, and delete. Fixture reports do not report accuracy or token-performance scores.
